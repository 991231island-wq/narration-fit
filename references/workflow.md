# 工作流与失败降级

## 步骤

1. 收集 `timeline.json`、全文、策略、语速、可选 `must_keep` 和上限。缺语速或策略：只提问，不改稿。
2. 先跑一遍时间轴。若用户还没有 `fit.json`，可以先写一份 `revised` 暂时等于 `original` 的 fit，让脚本把超预算的段标出来。
3. 对齐。每句原文要么出现在某段 `original`，要么出现在 `unassigned`。
4. 按策略改 `revised`。`trim` / `keep_faster` 主要压超预算段。`expand` 还要补明显偏短的段，补完仍不得超过预算；超预算段先修剪。
5. 校验。失败则只改失败段，重跑。
6. 渲染 HTML。把三份文件交给用户：`fit.json`、`diff.html`、`validation-report.md`。

## 失败时怎么停

| 情况 | 怎么做 |
|---|---|
| 时间轴重叠、`end_s` ≤ `start_s`、`segment_id` 重复 | 停止改稿。把脚本原文错误给用户，请用户改标注。不要为了过校验去改 `start_s` / `end_s` |
| 必留句比该段预算还长 | 不要删必留句来过关。告诉用户：加长该段（用户自己改时间轴），或改 `keep_faster` 并提高语速，或放宽必留句。三种都要用户选 |
| 必留句在改写时丢了 | 失败是对的。把句子放回同一段，改删其它内容 |
| `keep_faster` 仍超预算 | 按提示删字，或请用户确认更高语速。算出的语速若超过上限，只能删字，不能把上限私自抬高 |
| `expand` 超预算 | 先把该段压到预算内。不要用加字或加快语速掩盖。报告里的「先修剪」就是这个意思 |
| `expand` 仍偏短 | 警告，不失败。若用户不是故意留白，就在预算内继续补画面信息和过渡 |
| 未分配非空 | 默认失败。把句子划进某段，或请用户确认删掉后再清空 `unassigned` |
| 脚本缺失或不是 Python 3 | 说明需要本机 Python 3 标准库。不要改用云端接口顶替 |
| 用户要求读 mp4、做 TTS、自动精剪 | 拒绝放进 v1。记为未做。转写或 TTS 只给外链 |

## 单段修订

用户改了某一段的 `revised` 之后：

- 用原来的 `timeline.json` 和同一份 `fit.json` 重跑校验与渲染。
- 不要重新对齐其它段，不要重写没被点名的 `original`。
- 对照报告时，其它 `segment_id` 那一行的预算、原文字数、改后字数、超欠和 status 应不变。合计行允许变。

## 模型不负责的事

脚本不判断改完后的意思是否还对。交付时请用户抽查：必留句还在、数字和专名没有被改错、删掉的是修饰而不是结论。
