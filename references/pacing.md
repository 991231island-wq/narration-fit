# 语速、策略、字数

## 用户必须选定语速

`chars_per_sec` 是输入，不是脚本搜出来的最优值。报告里的「本次语速」必须等于用户这次给出的数字。

用户还没选时，只提供建议，等用户点头再写入 `fit.json`：

| 建议 | 数字 | 标签 |
|---|---|---|
| 舒适语速 | 4.7 字／秒 | 澄象创空间 README「自然讲课实测」参考值，**不是**行业标准，**不是**本 Skill 的实测 |
| 加快语速 | 5.5 字／秒 | 本 Skill 产品默认，**不是**口播实测。报告必须打印实际使用的数字，不能只写「加快档」 |
| 上限 | 6.0 字／秒 | 产品默认，用来挡住无上限加速。这个帽是否合理：**未核实** |
| 舒适区 | 3.5～4.7 | 上下界是否适合所有口音和方言：**未核实**，不要写成科学结论 |

脚本不会在用户选了 4.7 时偷偷改用 5.5。

## 策略

### trim

- 预算使用用户选定的语速，示例夹具用 4.7。
- 超预算就删减、合并句式。
- 有 `must_keep` 时，保住该句，删别的。
- 失败提示不提供「把语速调高就能过」。要更快，用户得改选 `keep_faster` 并给出新语速。

### keep_faster

- 预算使用用户选定的**更高**语速，示例夹具用 5.5。
- 目标是多留信息，而不是把原文原封不动地塞进去。原文若在 5.5 下仍然超，就要继续删，或者请用户把语速提到脚本算出的 X。
- X 不得超过 `max_chars_per_sec_cap`。超过帽时，提示在帽内语速下还要再删多少字。
- 通过时，Markdown 和 HTML 都要出现「本次语速: 5.5 字／秒」这种带具体数字的句子。

### expand

- 用在「这段画面很长，稿子太短，念完还空着」。
- 预算仍是用户选定的语速，示例夹具用 4.7。不靠加快语速把短稿变成「刚好」。
- 默认：原文少于 `budget × expand_short_ratio` 就算明显偏短。`expand_short_ratio` 默认 **0.7**，可在 fit 或命令行里改。
- 扩写只补画面里能看到的过程、过渡，以及原文里已经有、但写得太挤的信息。不换文风，不从零另写，不编造无关事实。
- 改后每一段都必须 `chars ≤ budget`。超了就失败，提示先修剪。
- 原文已经超预算时，先压到预算内，报告标「先修剪」，然后再看别的偏短段。
- 改完仍低于阈值：报告警告「仍偏短」，并写出 `under_by`。这本身不失败，避免把用户故意留的气口判死。
- `must_keep` 照旧必须留在同一段。

## 字数

v1 规则写死，Skill 1.1.0 没有改这条：

1. 去掉所有空白（空格、换行、全角空格等 Unicode 空白）。
2. 剩下的每个字符算 1，**标点计入**。
3. 不按词、不按英文单词折算。英文和数字也按字符计。

以后若改成「标点不计入」，必须把版本升到高于当时的 Skill 版本，并在当次报告写明。1.1.0 只增加 `expand`。

## 预算

```text
budget_chars = floor((end_s - start_s) × chars_per_sec)
```

实现使用十进制 `Decimal`，再向负无穷取整。例：10 秒 × 4.7 = 47，不是 46。

欠预算（改后字数少于预算）要标 `under_by`。`trim` 和 `keep_faster` 不因此失败。`expand` 对仍低于偏短阈值的段给出警告，同样不因此失败。留白可以，硬凑与画面无关的字不行。

## 未分配

允许存在 `unassigned` 字段，这样模型不能把没对齐的句子偷偷扔掉。默认校验：未分配字数大于 0 就失败，并打印原文。用户只是想先看对照时，可以给脚本加 `--allow-unassigned`。
